# pair/ — the live QR page

`wa_qr_live.py` is the whole reason this kit exists. It turns "link WhatsApp to this machine" into one command, and the QR into a picture in a browser that refreshes itself.

Written to be repaired by whoever is weakest at repairing it: what it does, in / out, who calls it, what breaks, how to tell, how to fix.

## What it does

1. Checks the environment: server installed, `QR_RAW` patch present in `dist/whatsapp.js`, `qrcode` module, `node` on PATH.
2. Starts **one** server client and never closes its stdin (an MCP stdio server shuts itself down the moment stdin closes).
3. Scrapes the raw QR string from the server log, renders `qr.png`, writes `status.json`.
4. Serves `http://127.0.0.1:8799` — QR + status + generation counter. The markup is generated by this same file, so there is one source of truth.
5. Detects the moment `auth_info/creds.json` appears → the page says done, the bridge is killed, the process exits 0.

The scan itself cannot be automated: WhatsApp accepts a companion device only from the owner's phone. Everything else around it is here.

## In / out

|  |  |
|---|---|
| input | nothing required. Flags: `--check` · `--selftest` · `--heal-patch` · `--port N` (default 8799) · `--timeout-sec N` (default 900) · `--force` · `--no-open` |
| output | page at `http://127.0.0.1:<port>` and files in the work dir: `qr.png`, `qr_string.txt`, `status.json`, `index.html`, `server.log` |
| exit codes | `0` linked · `1` timeout / no QR · `2` already linked · `3` environment not ready (also: `--heal-patch` that could not patch) · `4` crash |
| env | `WHATSAPP_MCP_DIR` (server location; default = auto-detect via `npm root -g`) · `WHATSAPP_MCP_AUTH_DIR` (default = the server's own `~/.local/share/whatsapp-mcp/auth_info`) · `WA_QR_WORK_DIR` (default `~/.whatsapp-mcp-kit`) |

`status.json` is the contract with the page: `{state: BOOT|QR|WAIT|LINKED|TIMEOUT, generation, qr_at, note}`. A rising `generation` means the loop is alive. Not rising for over a minute means the bridge is stuck.

## What breaks, and how to tell

| symptom | root cause | fix |
|---|---|---|
| "no QR", no `QR_RAW_BEGIN` in `server.log` | `npm update` wiped the vendor patch | `--heal-patch`, then run again |
| phone: "check your connection and try again later" | you scanned an EXPIRED code (~20s life) | scan the one on the page right now; it is always fresh |
| `AUTH_KEY_DUPLICATED`, the link keeps dropping | two clients on one link | `--check` lists live ones; kill them, but see gotcha 7 — a node whose parent is a live client is legitimate |
| exit 3 "environment not ready" | no server / no `qrcode` / no `node` | the message names exactly what is missing |
| port 8799 busy | someone else's server | it auto-tries 8800-8804; or `--port 9100` |
| ASCII soup in the terminal | expected on Windows fonts | not a failure — look at the **page**, not the console |
| page says "bridge is reconnecting" | gap between codes longer than 3 min | **wait.** This is normal; the server comes back on its own |
| exit 1 "bridge keeps dying" | the server really is crashing at startup | read `server.log` — usually environment: no write permission on `store/`, corrupt `whatsapp.db` |

⚠️ **Never rebuild a live client.** Measured 2026-08-05, both halves of one evening: the hands-off run produced **17 codes in a row**; the run where the tool "healed" pauses by killing the client produced **2 codes per client**, three rebuilds, and gave up after 4 minutes. WhatsApp throttles frequent reconnects. We respawn only a process that is genuinely dead (`child.poll() is not None`). The `STALE_SEC=180` threshold exists purely to put an honest line on the page; it kills nothing.

⚠️ **A responding profile and a chat list are NOT proof of a live link** — they are served from local cache and lied to us for 26 days straight. Proof = credentials present **and** data fresh, checked by a different tool than the one that owns the bridge.

## Verify

```bash
python wa_qr_live.py --check       # diagnosis, zero side effects
python wa_qr_live.py --selftest    # proves the part can work (no phone, no network)
python test_wa_qr_live.py          # 27-check regression
```

The 27 checks need no network, no phone and no server installed. It goes red on broken code — verified by mutation (re-introducing the crash-guard bug turns checks red, not green).

## Boundaries

Sends no messages. Does not touch `store/whatsapp.db` (your history) and never deletes auth. Does not fix *delivery*: a paired bridge is not a working outbound channel — that is a separate concern.
