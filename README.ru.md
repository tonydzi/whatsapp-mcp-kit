# WhatsApp для Claude Code и Codex

Дата сверки: 24 октября 2026. Этот документ дополняет [существующий комплект](https://github.com/tonydzi/whatsapp-mcp-kit), а не устанавливает новый мессенджер.

## Что подключаем

Один стек: MCP-сервер `@sjawhar/whatsapp-mcp` поверх Baileys и WhatsApp linked device. Claude Code и Codex обращаются к одному владельцу соединения через MCP. Второй аккаунт означает второй приватный каталог данных, отдельный lock и отдельного владельца. Два аккаунта не создают вторую независимую технологическую рельсу.

Это не официальный WhatsApp Business Cloud API. Сначала владелец выбирает аккаунт и принимает риск ограничений неофициального клиента. Upstream рекомендует отдельный номер. Возможность прочитать переписку также означает, что выбранный AI-провайдер увидит переданные ему результаты инструментов. Начинайте с небольшого разрешённого фрагмента, не со всего архива.

## Что уже есть и что остаётся проверить у вас

| Часть | Статус комплекта |
|---|---|
| MCP-сервер | Локально исследован установленный npm-пакет 2.4.0. Его runtime содержит дополнительные локальные патчи; номер версии не доказывает идентичность чистому npm-пакету |
| QR | В публичном комплекте есть `pair/wa_qr_live.py`, патчи и офлайн-регрессия. Перед использованием учтите исправление определения привязки ниже |
| Код по номеру телефона | Поддерживается API Baileys `requestPairingCode`. В исходном публичном комплекте нет готового переносимого CLI для этой ветки. Нельзя выдумывать флаг `--phone` для MCP-сервера |
| Два AI-клиента | Чистый npm 2.4.0 предоставляет HTTP owner и proxy. Нужен один контролируемый owner и два HTTP MCP-клиента. HTTP-ветка этой версии не защищена stdio lock |
| Телефон пользователя | В этой редакции не привязывался. QR и phone-code не испытаны заново на новом аккаунте |

Источники: [публичный kit](https://github.com/tonydzi/whatsapp-mcp-kit), [настоящий upstream сервера](https://github.com/sjawhar/whatsapp-mcp-2.0), [Baileys: подключение и код по номеру](https://github.com/WhiskeySockets/Baileys/blob/master/README.md#connecting-account). Не перепутайте npm-имя с URL репозитория.

## Установка скилла в оба клиента

Склонируйте публичный kit и проверьте выбранный commit. Скопируйте только каталог `skills/whatsapp-connect/` в `~/.claude/skills/whatsapp-connect/` для Claude Code и `~/.codex/skills/whatsapp-connect/` для Codex. На Windows `~` означает профиль пользователя; на macOS/Linux домашний каталог. Если каталог уже существует, сравните версии и сделайте приватную резервную копию до обновления. Полные публичные ссылки внутри SKILL работают без соседних файлов.

Откройте свежую сессию и явно вызовите skill по имени. Обнаружение инструкции не подтверждает авторизацию WhatsApp или MCP. Если интерфейс клиента не обнаружил skill, передайте ему проверенный SKILL.md как инструкцию вручную, не создавая новый WhatsApp owner.

Проверенный upstream tag `v2.4.0` разрешён в commit `fe65c2d51fd9964b91ac3296263ed24778b03881` ([исходник](https://github.com/sjawhar/whatsapp-mcp-2.0/tree/fe65c2d51fd9964b91ac3296263ed24778b03881)). Он подтверждает HTTP CLI; локальные дополнительные broker-патчи не входят в чистый пакет.

## 1. Сначала инвентаризация

Перед установкой агент должен перечислить существующие WhatsApp MCP-определения в ОБОИХ клиентах, процессы, service/task owner, выбранный приватный data root и слушающий порт. Выводите только названия, версии, PID, состояние и пути без содержимого секретов. Не запускайте сервер ради `--help`: некоторые версии игнорируют неизвестные флаги и сразу подключаются.

```text
node --version
python --version
git --version
npm root -g
npm ls -g @sjawhar/whatsapp-mcp --depth=0
claude mcp list
codex mcp list
```

Прочитайте `package.json`, `dist/index.js`, `dist/paths.js`, `dist/http-server.js`, `dist/connect-proxy.js` именно установленной версии. Проверьте `--http`, bind host, `/mcp`, способ bearer-аутентификации, `--connect` и его env. Эти файлы не содержат account auth state, но всё равно не печатайте целиком пользовательские конфиги и `.env`.

В исследованном runtime `--connect` является переключателем, а URL берётся из `WHATSAPP_MCP_URL`. Команда `--connect http://...` сама по себе не задаёт URL. HTTP owner требует `MCP_API_KEY`; stdio proxy читает `MCP_API_KEY` либо `WHATSAPP_MCP_SECRET`. Автоматическое обнаружение owner через `.broker.json` является дополнительным локальным патчем. На чистом upstream его наличие не предполагается.

## 2. Установка в отдельный каталог

Если уже есть работающий экземпляр, используйте его и не переустанавливайте глобально. Если его нет, возьмите комплект и закрепите версию сервера:

```text
git clone https://github.com/tonydzi/whatsapp-mcp-kit <KIT_DIR>
```

В новом каталоге `<SERVER_DIR>`:

```text
npm init -y
npm install --save-exact @sjawhar/whatsapp-mcp@2.4.0
```

Это устанавливает программу и её install scripts, поэтому до исполнения агент показывает источник и выбранный каталог. Пакет использует `better-sqlite3`; несовместимый Node ABI может потребовать подходящий поддерживаемый Node и native build tools. Нижний предел `node >=18` из package metadata не является рекомендацией использовать устаревший Node 18. Используйте поддерживаемый Node LTS и запишите фактическую версию.

`<MCP_DIR>` теперь равен `<SERVER_DIR>/node_modules/@sjawhar/whatsapp-mcp`. Созданный lockfile сохраните вместе с частным проектом конфигурации. Не выполняйте `npm update` во время настройки: патчи QR и group names привязаны к конкретным байтам. В `<MCP_DIR>` сначала `git apply --check <KIT_DIR>/patches/0001-qr-raw-to-stderr.patch`, затем примените проверенный патч. Патч 0002 проверяется отдельно; конфликт не разрешайте принудительным fuzzy patch.

Вместо глобальных зависимостей Python создайте venv в `<KIT_DIR>/.venv` и установите `qrcode pillow`. На Windows интерпретатор обычно `.venv/Scripts/python.exe`; на macOS/Linux `.venv/bin/python`. Далее `<PYTHON>` означает этот интерпретатор.

## 3. Выбор каталогов и секретов

| Переменная | Назначение |
|---|---|
| `WHATSAPP_MCP_DIR` | Каталог установленного npm-пакета для QR helper |
| `XDG_DATA_HOME` | Приватный корень конкретного аккаунта, даже на Windows |
| `WA_QR_WORK_DIR` | Приватные временные QR/status/log файлы helper |
| `MCP_API_KEY` | Случайный секрет локального HTTP owner, загружается вне Git |
| `WA_MCP_TOKEN` | Та же строка, доступная HTTP-клиентам из защищённого окружения |
| `ALLOWED_SEND_DIR` | Отдельная абсолютная папка для разрешённых отправок файлов |

Путь аккаунта вычисляется как `<XDG_DATA_HOME>/whatsapp-mcp/`. Внутри находятся `auth_info/`, `store/`, lock, переписка и другие приватные данные. Имя MCP-сервера `whatsapp2` аккаунт не выбирает. Флаг `--wa-account=...` из некоторых локальных примеров тоже не выбирает аккаунт: это был диагностический маркер.

Не храните auth, SQLite, QR, pairing code, `.env`, bearer token или broker descriptor в репозитории. QR и pairing code дают право привязать устройство и являются временными секретами. Не публикуйте их на GitHub и не отправляйте в чужую AI-сессию.

## 4. Привязка через QR

Перед pairing убедитесь, что ни owner, ни другая pairing-сессия не владеют тем же каталогом. Если владелец жив, согласуйте остановку именно его, а не убивайте все `node` на машине. Не используйте `--force` по умолчанию. Каталог `auth_info` не удаляйте для обхода проверки.

Настройте переменные среды только для pairing-процесса. PowerShell:

```powershell
$env:WHATSAPP_MCP_DIR = '<MCP_DIR>'
$env:XDG_DATA_HOME = '<PRIVATE_ACCOUNT_DATA_ROOT>'
$env:WA_QR_WORK_DIR = '<PRIVATE_QR_WORK_DIR>'
& '<PYTHON>' '<KIT_DIR>/pair/wa_qr_live.py' --check
& '<PYTHON>' '<KIT_DIR>/pair/wa_qr_live.py'
```

macOS/Linux:

```sh
export WHATSAPP_MCP_DIR='<MCP_DIR>'
export XDG_DATA_HOME='<PRIVATE_ACCOUNT_DATA_ROOT>'
export WA_QR_WORK_DIR='<PRIVATE_QR_WORK_DIR>'
'<PYTHON>' '<KIT_DIR>/pair/wa_qr_live.py' --check
'<PYTHON>' '<KIT_DIR>/pair/wa_qr_live.py'
```

Откройте адрес, который вывел helper: при занятом порте он может выбрать следующий. На телефоне: WhatsApp → Связанные устройства → Привязка устройства. Сканируйте текущую картинку. Сообщение телефона об ошибке связи может быть вызвано истёкшим QR, но не доказывает эту причину: проверьте поколение кода, время и логи.

Пауза между QR не означает смерть процесса. Не создавайте второй клиент из-за паузы и не перезапускайте живой socket в цикле. Не закрывайте stdin stdio-серверу во время pairing: он воспринимает EOF как завершение клиента.

**Привязка не равна свежей связи.** Непустой `creds.json`, `me.id`, флаг `registered`, профиль или список старых чатов по отдельности ничего не доказывают. Исправленный helper требует структурные признаки `account` и непустой `signalIdentities`. Это проверка формы сохранённого состояния, а не криптографическая проверка подписей и не доказательство текущего соединения. Свежая связь подтверждается отдельным входящим тестовым сообщением после времени старта.

## 5. Если экран недоступен: код по номеру

Это другой способ привязать тот же linked device, не вторая WhatsApp-рельса. Upstream Baileys предоставляет `requestPairingCode` и событие `connection.update`. Номер задаётся цифрами с кодом страны, без `+`, пробелов и скобок. Пользователь вводит выданный код в WhatsApp → Связанные устройства → Привязка по номеру телефона, если эта опция доступна в его версии приложения.

Готового phone-code CLI исходный публичный kit не содержит. Дайте агенту [PROMPT-PHONE-CODE.ru.md](PROMPT-PHONE-CODE.ru.md). Он обязан сначала проверить поддержку у выбранного установленного сервера, затем использовать существующий поддерживаемый onboarding-инструмент. Если такого инструмента нет, честный результат `PHONE_CODE_NOT_IMPLEMENTED_IN_THIS_KIT`, а не команда с выдуманным флагом. QR остаётся штатным исполняемым путём этого комплекта.

Нельзя одновременно запустить отдельный Baileys pairing-client и существующий owner на одной auth-папке. Получение кода и появление credentials до ввода кода не считаются успешной привязкой. Код не сохраняется в обычный лог или отчёт. После `restartRequired` требуется аккуратно передать сохранённый state единственному owner и проверить соединение заново.

## 6. Один owner для Claude Code и Codex

После pairing helper должен завершиться и освободить socket. Для подтверждённой версии с HTTP-режимом запускайте owner в отдельном управляемом процессе:

```text
node <MCP_DIR>/dist/index.js --http --host 127.0.0.1 --port <ACCOUNT_PORT>
```

Этот процесс получает свой `XDG_DATA_HOME`, `MCP_API_KEY` и абсолютный `ALLOWED_SEND_DIR` из защищённого окружения. Секреты не передаются через argv. Не используйте host `0.0.0.0`. Перед запуском проверьте, что порт свободен; чужой listener не убивайте. HTTP 401 без ключа означает, что аутентификация работает, но не доказывает живой WhatsApp.

**В чистом npm 2.4.0 HTTP-ветка вызывает initWhatsApp без stdio acquireWhatsAppLock.** Поэтому «один owner» здесь является правилом эксплуатации: один supervisor на аккаунт, запрет ручного второго запуска и отдельные data roots. На Windows задайте `MultipleInstances=IgnoreNew`; на macOS/Linux запускайте единственный именованный service/unit. Проверка PID перед ручным стартом не устраняет гонку. Не считайте встроенный stdio lock защитой HTTP-ветки и не запускайте вторую HTTP-копию на другом порте того же аккаунта.

Далее оба AI-клиента подключаются к `http://127.0.0.1:<ACCOUNT_PORT>/mcp` через native HTTP. Примеры находятся в `configs/`; число 8791 в них является примером, выберите порт своего owner. Claude JSON умеет подставлять `${WA_MCP_TOKEN}` в headers. В Codex используется `bearer_token_env_var`; подстановка `${VAR}` внутрь произвольного TOML сама по себе не предусмотрена.

Вариант Codex CLI, после замены placeholder и при наличии токена в окружении процесса Codex:

```text
codex mcp add whatsapp --url http://127.0.0.1:<ACCOUNT_PORT>/mcp --bearer-token-env-var WA_MCP_TOKEN
```

Не запускайте полный stdio server в каждой Claude/Codex-сессии. Если клиент не поддерживает native HTTP, возможен тонкий `--connect` proxy, только после проверки точного CLI и env выбранной версии. Это транспортный adapter к тому же owner, не независимая connection rail.

Запуск HTTP listener не доказывает, что единственный owner открыл socket; HTTP-lock этой версией не обеспечивается. Проверьте authenticated MCP initialize → tools/list → разрешённое чтение → новый входящий canary. Не пишите `GREEN`, если доступны только кэшированные чтения.

Автозапуск оформляется после ручной приёмки одним сервисом на аккаунт: Windows Task Scheduler, macOS LaunchAgent или Linux systemd user service. Укажите абсолютный `node`, entrypoint, cwd, data root и безопасную загрузку ключа. Проверьте свежий процесс и входящее после перезапуска owner. Не распространяйте живую auth-папку на второй компьютер.

## 7. Приёмка без рассылки

1. Запишите время начала и разрешённый тестовый чат. Владелец телефона вручную отправляет туда уникальный nonce после этой отметки.
2. Claude и Codex независимо читают его через общий owner. Сверьте account, chat ID, message ID, nonce и время. В отчёт помещайте идентификаторы теста с разрешения владельца, без переписки.
3. Две AI-сессии не должны создавать второй WhatsApp socket или переходить в read-only из-за lock-войны.
4. Подготовьте тестовый исходящий черновик. Отправляйте только после разрешения владельца на конкретный адрес и текст. Сохраните provider message ID и прочитайте тот же объект обратно. Получение/прочтение адресатом проверяется отдельно.
5. После timeout отправки статус `UNKNOWN`, а не `FAILED`: сначала поищите nonce/message ID, повтор вслепую создаёт дубли.
6. Перезапустите только принадлежащий этому setup owner по согласованному шагу. Убедитесь, что связка снова читает новый canary, не только старый кэш.

Профиль, наличие tools, живой порт, QR exit 0 и локальный store являются отдельными фактами. Их нельзя склеивать в утверждение «двусторонняя доставка проверена».

## 8. Типовые поломки

| Симптом | Проверка и ограниченное действие |
|---|---|
| Another process / read-only | Проверьте реального владельца и XDG root; подключите клиента к owner. QR обычно не лечит конфликт lock |
| Старые чаты возвращаются, новых нет | Сверьте новый входящий nonce, owner socket и время данных. Перечень чатов может читаться из SQLite без сети |
| После npm update нет QR | Сверьте package version и `git apply --check`; не объявляйте патч установленным по одному имени файла |
| Node остался после Python | На Windows родительский terminate не гарантирует завершение дерева. Проверьте PID/parent; завершайте только дерево, которое создали сами |
| Другой аккаунт вместо нужного | Имя MCP не выбирает аккаунт. Сверьте XDG data root во всех owner/pairing/reader конфигурациях |
| 401 | Проверьте bearer environment и правильный endpoint. Не обходите auth |
| Нет многолетней истории | Измерьте фактическую глубину. Linked-device sync может дать много данных, но полнота архива не гарантируется; нужен отдельный экспорт/backup-процесс |
| Телефон требует повторную привязку | Сначала отличите logout от lock/port/cache проблемы. Не удаляйте credentials и не копируйте их между машинами |
